WALK-IN TO MOBILE APP ACCOUNT CONVERSION PLAN
================================================================================
Project: Infinity Wash Laundry App
Date Created: 2026-09-29
Status: PLANNED (Not yet implemented)

================================================================================
OVERVIEW
================================================================================

GOAL:
Allow walk-in customers to convert their existing walk-in account into a 
mobile app account, preserving their order history and customer code.

USER STORY:
"As a walk-in customer, I want to register in the mobile app using my existing
customer code so that I can view my past orders and continue using the same 
account."

BUSINESS VALUE:
- Seamless customer experience (no duplicate accounts)
- Preserved order history
- Encourages walk-in customers to use the mobile app
- Single source of truth for customer data

================================================================================
CURRENT STATE (as of 2026-09-29)
================================================================================

CUSTOMER TYPES:
1. Walk-in customers:
   - Created by staff during order creation
   - Have customer_code (e.g., "CUST-00014")
   - Have NO profile_id (not linked to auth.users)
   - Have NO app account
   - customer_type = 'walk_in'

2. Mobile app customers:
   - Self-registered through mobile app
   - Have customer_code (e.g., "CUST-00015")
   - Have profile_id (linked to auth.users)
   - Can sign in to app
   - customer_type = 'mobile_app'

CURRENT CUSTOMER TABLE STRUCTURE:
- id (UUID) - primary key
- customer_code (TEXT) - unique (e.g., "CUST-00014")
- profile_id (UUID) - nullable, links to profiles table
- first_name, last_name, phone, email, address, landmark
- customer_type ('walk_in' or 'mobile_app')
- status ('active', 'inactive', etc.)
- joined_at, created_at, updated_at

CURRENT REGISTRATION FLOW (Mobile App):
1. User fills registration form (email, password, name, phone, address)
2. Supabase Auth creates user in auth.users
3. Trigger handle_new_auth_user() creates:
   - Profile in profiles table
   - Customer in customers table with NEW customer_code
4. Result: New mobile_app customer with no connection to walk-in history

================================================================================
PROPOSED SOLUTION
================================================================================

CONVERSION FLOW:
1. During registration, user can enter an OPTIONAL "Customer Code" field
2. If customer code provided:
   a. Verify customer code exists and is walk-in type
   b. Verify customer code is not already linked to another account
   c. Create auth account and profile as normal
   d. LINK existing customer record instead of creating new one:
      - Update existing customer's profile_id
      - Update customer_type from 'walk_in' to 'mobile_app'
      - Keep original customer_code and order history
3. If customer code NOT provided or invalid:
   - Normal registration flow (create new customer)

DATABASE SCHEMA REFERENCE
================================================================================

CUSTOMERS TABLE (current):
- id: UUID (PK)
- customer_code: TEXT (UNIQUE) ← Key field for linking
- profile_id: UUID (FK to profiles) ← NULL for walk-in, set on conversion
- customer_type: TEXT ← Changes from 'walk_in' to 'mobile_app'
- first_name, last_name, phone, email, address, landmark
- status, joined_at, created_at, updated_at

PROFILES TABLE (current):
- id: UUID (PK)
- supabase_user_id: UUID (FK to auth.users)
- first_name, last_name, email, phone, address, landmark
- role: TEXT ('customer')
- status: TEXT ('active')

ORDERS TABLE (unchanged):
- customer_id: UUID (FK to customers) ← Links remain intact after conversion

================================================================================
EDGE CASES TO HANDLE
================================================================================

1. Customer code doesn't exist
   → Show error: "Customer code not found. Leave blank to create new account."

2. Customer code already linked to another account
   → Show error: "This customer code is already linked to an account."

3. Customer code is for mobile_app type (not walk_in)
   → Show error: "This customer code is already a mobile app account."

4. Name/phone mismatch during verification
   → Show warning: "Name on file: John Doe. Continue?" (let user confirm)

5. User forgets their customer code
   → Support staff can look up by phone number
   → Add "Forgot customer code?" link → contact support

6. Duplicate registration attempts
   → Normal Supabase auth duplicate email error handling

================================================================================
NOTES & DECISIONS
================================================================================

DECISION 1: Customer code field is OPTIONAL during registration
Reason: Don't force users to have a code; new customers can still register normally

DECISION 2: Use trigger-based linking (not app-side)
Reason: Keeps logic centralized in database, reduces race conditions

DECISION 3: Allow name/email updates during conversion
Reason: Walk-in data might be incomplete or outdated

DECISION 4: Keep original customer_code after conversion
Reason: Preserves referential integrity with existing orders

DECISION 5: Update customer_type on conversion
Reason: Track which customers converted vs. initially registered via app
