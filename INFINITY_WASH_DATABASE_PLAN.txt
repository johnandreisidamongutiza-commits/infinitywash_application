INFINITY WASH - FINAL MERGED DATABASE PLAN
==========================================

Purpose
-------
This plan combines the web management system and the separate application side.
It keeps Supabase as the permanent source of truth and Firebase as the source
of continuously changing data.

SYSTEM SIDES
------------

Web management system:
- Admin
- SuperAdmin

Separate application side:
- Customer
- Staff
- Rider

The two sides may use different frontends and login screens, but they share the
same permanent business records through the backend.

DATA OWNERSHIP RULE
-------------------

Supabase stores what happened and must be retained:
- Profiles and role assignments
- Customers, staff, and riders
- Orders and payments
- Services and pricing
- RFID registration and scan history
- Dispatch jobs
- Inventory and inventory movement history
- Feedback
- Audit logs
- Backup metadata

Firebase stores what is happening right now:
- Rider online status and location
- Live order progress
- Current RFID/device state
- Device heartbeats
- Live notifications
- Chat messages
- Push notification tokens

Firebase must not be the permanent source of truth for orders, payments,
feedback, inventory history, or customer history.

============================================================
1. SUPABASE AUTHENTICATION
============================================================

Supabase Auth is the single authentication provider for Admin, SuperAdmin,
Customer, Staff, and Rider. Credentials and sessions are managed by Supabase
Auth, not by tables. The separate web and application interfaces are selected
after login using the role stored in the permanent profile.

No password columns are stored in Supabase or Firestore.

============================================================
3. FILE STORAGE AND FREE-TIER RULES
============================================================

Use Supabase Storage for permanent files:
- profile pictures
- delivery proof files
- receipt files
- backup files

Store only the file path or URL in the related Supabase table. Do not store
binary files inside PostgreSQL rows or upload the same file to both services.

Firebase Firestore stores small realtime documents only. Chat attachments
should use one selected storage provider, preferably Supabase Storage, with
only the file URL and message metadata kept in Firebase.

Exact free-tier quotas can change, so verify the current Supabase and Firebase
limits before deployment. The design reduces usage by keeping files small,
compressing images, limiting upload sizes, expiring temporary notifications,
removing stale live-state documents, and retaining only the required backup
history.

Do not use Firebase for permanent file archives or duplicate Supabase files.
Do not use realtime listeners for historical lists that can be read from
Supabase when the screen opens.

============================================================
5. DUPLICATE DATA DECISIONS
============================================================

The Firebase `users` collection is not a second permanent user table. Supabase
Auth owns login identity, while Supabase `profiles`, `customers`, and
`employees` own permanent identity and business data. Only live application
state such as online status and FCM token belongs in Firebase.

The Firebase `orders` collection becomes `live_orders`. It contains only live
status/progress and references the permanent Supabase order.

The Firebase `inventory` collection is removed as a permanent collection.
Current inventory quantity and movement history belong in Supabase. A live
inventory alert may be delivered through Firebase notifications.

The Firebase `rfid_tags` collection becomes `live_rfid`. Tag registration and
permanent scan history belong in Supabase.

The Firebase `feedback` collection is removed. Feedback belongs permanently in
Supabase.

The Firebase `notifications` collection remains realtime and references
permanent Supabase records where needed.

The Firebase `chats` and `rider_tracking` collections remain Firebase-only
realtime features.

============================================================
6. RELATIONSHIPS
============================================================

profiles 1-to-0/1 admin_accounts
profiles 1-to-0/1 customers
profiles 1-to-0/1 employees
customers 1-to-many orders, payments, and feedback
employees 1-to-many assigned orders and dispatch_jobs
orders 1-to-many payments, dispatch_jobs, inventory_movements, and feedback
orders 1-to-many order_addons
orders 1-to-0/1 active RFID tag
rfid_tags 1-to-many rfid_scans
inventory_items 1-to-many inventory_movements

============================================================
7. RULES
============================================================

1. Supabase is authoritative for permanent data.
2. Supabase Auth is the only authentication provider for all five roles.
3. Firebase is authoritative only for continuously changing data.
4. Every Firebase live document that represents a Supabase record stores the
   corresponding Supabase ID.
5. Keep permanent core tables normalized, but allow explicit historical
   snapshots and current-value caches where they reduce reads or preserve past
   values.
6. `orders.service_name`, `order_addons.addon_name`, and order address fields
   are historical snapshots; they must not be treated as live catalog data.
7. `inventory_items.quantity` is the current balance; `inventory_movements`
   remains the permanent movement history.
8. `rfid_tags.active_order_id` is the single permanent current-assignment
   pointer; RFID scans hold historical events.
9. Do not store passwords in either database.
10. Do not store raw API keys in either database.
11. Do not create a branches table or branch foreign keys.
12. Do not create employee shift columns; this store does not use shifts.
13. Do not duplicate permanent orders, payments, feedback, or inventory history
   in Firebase.
14. Important completed Firebase events, especially RFID scans and dispatch
   completion, are written to Supabase through the backend.
15. Do not create separate KPI or analytics tables. Calculate summaries from
    permanent orders, payments, inventory movements, and feedback.
16. Keep actual backup files in object storage and store only their metadata in
    Supabase.
